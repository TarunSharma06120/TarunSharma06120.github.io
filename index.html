Case study · CRMIT Solutions · Agentforce

Resource Allocation Agent

An Agentforce agent that answers managers' staffing questions right in chat, and replies with a custom Lightning Web Component instead of a wall of text.

Role: built the agent action and the LWCAgentforce · Apex · LWC · SOQL

The problem

To see who was working on what, managers had to open reports, filter by project and add up hours themselves. The questions were simple, but getting answers was slow.

What managers want to know

  • Who is working on project X, and for how many hours?
  • How many hours is a given employee allocated across all projects?
  • Who has spare capacity for new work, and who is fully booked?
  • Which projects is my team spread across right now?

What I built

  • Agent topic and action: the manager asks in plain language and Agentforce routes the question to an allocation action.
  • Apex logic: the action queries allocation records and returns employees, projects and allocated hours.
  • LWC rendered in chat: instead of a text answer, the agent shows a component listing each employee with their projects and hours, so it can be scanned at a glance.

How it flows

  1. ManagerAsks: who is on project X?
  2. AgentforcePicks the allocation topic and action
  3. ApexQueries allocations and hours
  4. LWC in chatShows employees, projects and hours

Why a component instead of text

  • Hours and project lists are tabular data, which reads far better as a table than as sentences.
  • The same component can be reused anywhere in Salesforce, not only in the agent.

Outcome

Managers get staffing answers in seconds by asking a question, without building or filtering reports.

Case study · CRMIT Solutions · LWC

Employee Efficiency Dashboard

An Apex controller and LWC that chart each employee's expected versus actual performance with Chart.js, with hover values and time filters.

Role: built the controller and the dashboardApex · LWC · Chart.js · SOQL

The problem

Leads wanted to compare what each person was expected to deliver against what they actually delivered, over different periods, and spot the gap quickly.

Why Chart.js instead of standard reports

  • Two series on one chart: expected and actual performance side by side for the same employee and period.
  • Exact values on hover: tooltips show the precise number for each point, so nobody has to guess from the axis.
  • Custom filters: switch the chart to a particular week or time range without building a new report.
  • Full control inside an LWC: layout, colours and interactions fit the page instead of being limited to standard dashboard components.

What I built

  • Apex controller: aggregates expected and actual figures by employee and period and returns them to the component.
  • LWC: loads Chart.js from a static resource, draws the expected and actual series, and re-renders when filters change.
  • Filters: week and date-range selection drive new data from the controller.

How it flows

  1. LeadPicks an employee and a week or range
  2. ApexReturns expected and actual totals
  3. Chart.jsDraws both series together
  4. HoverShows exact values per point

Outcome

Expected and actual performance became one interactive chart that leads can filter by week, instead of separate reports to compare by hand.

Case study · CRMIT Solutions

Skill Tracking & Approval Portal

An internal Salesforce portal where employees manage their skills, managers approve them, and every level of the company is emailed the gaps it is responsible for.

Role: designed and built it end to endApex · LWC · SOQL · HTML email

The problem

Nobody had one reliable view of who knew what. Skills lived in people's heads and spreadsheets, so managers could not see gaps in their teams, and branch heads and HR could not see gaps across branches or the company.

What I built

  • Skills LWC: employees add new skills and remove ones that no longer apply.
  • Approval before visibility: each new skill goes to the employee's manager for approval. Only approved skills appear to the employee, managers, branch head, CCM and HR.
  • Employee Skills controller (Apex): handles adding, removing, approving and querying skills, and builds the summaries.
  • Notifications: when a request is decided, both the employee and the manager get an email.
  • Missing-skill digests: each level gets an email table of employees and the names of the skills they are missing.

How the data flows

  1. EmployeeAdds or removes a skill in the LWC
  2. ManagerApproves it; both get an email, plus a table of their reports' missing skills
  3. Branch headTable of everyone in the branch with missing skill names
  4. HRThe same table for the whole company

Design decisions

  • Skills are visible only after approval, so the record stays trustworthy.
  • One controller serves every audience, so each digest is the same query scoped by manager, branch or company.
  • Emails are plain HTML tables, so they read well in any mail client without logging in.

Outcome

Skills became an approved record instead of guesswork, and every level, from team managers to HR, regularly sees the missing skills in its own area.

Case study · Metadologie · 2GP

Meta Tax Calculator

A generic second-generation managed package that calculates tax through Avalara for any object, configured by field names instead of custom code.

Role: designed and built the packageApex · Schema describe · Avalara API · Flow · 2GP

The problem

Several projects needed tax calculation, and each one was about to rebuild the same Avalara integration for its own objects.

What I built

  • Generic inputs: a record Id plus the names of the fields that hold quantity, address and product, the field to write the tax into, and a field for error messages.
  • Works on any object: from the record Id, the package uses the Schema class to identify the object and read the configured fields dynamically.
  • Avalara callout: sends the quantity, address and product to Avalara and reads back the tax.
  • Writes the result back: the tax goes into the specified tax field. If anything fails, the reason is stored in the error field.
  • Callable anywhere: from Apex and from Flow.

How it flows

  1. Apex or FlowPasses record Id and field names
  2. SchemaFinds the object and reads the fields
  3. AvalaraCalculates the tax
  4. RecordTax or error saved to the chosen fields

Design decisions

  • Configuration over code: a new object needs field names, not a new class.
  • Errors are saved on the record, so admins can see what went wrong without reading logs.
  • Packaged as a 2GP so it installs cleanly and versions across orgs.

Outcome

One reusable package replaced per-project tax integrations, and any object in any org could get Avalara tax by configuration.

Case study · Metadologie · Simulator Components

Invoice Tax Without Extra Callouts

Logic that reuses the tax already calculated on Sales Order lines when they are invoiced, so invoices get accurate tax without calling Avalara again.

Role: designed and built the logicApex · Triggers · Avalara API

The problem

Sales Orders and their lines already had tax calculated through Avalara. When an order was converted into an Invoice and Invoice Lines, the system called Avalara again for the same goods, adding callouts for numbers we already had.

What I built

  • When lines are converted to an invoice, the logic reads the tax already stored on each Sales Order line instead of calling Avalara.
  • It calculates tax per unit from the order line and applies it to the quantity actually being invoiced, so partial conversions stay accurate.
  • The invoice total tax is the sum of its lines, however many lines or orders are converted.

Worked example

A Sales Order has 3 lines totalling ₹300, with ₹30 tax calculated by Avalara (₹10 per line). One line has a quantity of 10 units and ₹10 tax, so ₹1 per unit. Only 5 of those 10 units are converted to an invoice.

StepValue
Order line tax₹10 for 10 units
Tax per unit₹10 ÷ 10 = ₹1
Units invoiced5
Invoice line tax5 × ₹1 = ₹5
Avalara callouts at invoice0

How it flows

  1. Sales OrderAvalara calculates tax per line once
  2. ConvertLines or partial quantities move to an invoice
  3. My logicTax per unit × units invoiced
  4. InvoiceLine and total tax, no new callout

Outcome

Invoices carry the same tax as their orders, partial quantities included, and the invoice step no longer makes Avalara callouts.

Case study · CRMIT Solutions · UnitedHealthcare

UHC Kafka API Integration

A Java Spring Boot middleware that keeps Salesforce in real-time sync with events arriving on Kafka for UnitedHealthcare.

Role: built the middlewareJava · Spring Boot · Kafka · Salesforce APIs

The problem

UnitedHealthcare needed Salesforce to reflect changes as they happened. Events were published to Kafka, and each one had to become a create, update or delete in Salesforce without manual steps or batch delays.

What I built

  • Spring Boot consumer: listens to the Kafka topics and receives each event as it arrives.
  • Mapping layer: turns the event payload into the matching Salesforce object and fields.
  • CRUD in Salesforce: creates, updates or deletes the record through the Salesforce APIs, depending on the event.
  • Built for volume: designed to keep up with a high-throughput stream of events.

How it flows

  1. Source systemPublishes an event to Kafka
  2. Spring BootConsumes and maps the event
  3. Salesforce APICreate, update or delete
  4. SalesforceRecord is current in real time

Why middleware in Java

  • Keeps Kafka handling outside Salesforce, so the org only receives clean API calls.
  • Spring Boot gives mature Kafka support and a simple place to add mapping rules.

Outcome

Salesforce stays in sync with Kafka events in real time, with no manual updates or batch jobs.
